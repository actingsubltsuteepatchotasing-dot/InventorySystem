# Overview
จัดทำโปรแกรมควบคุมสินค้าคงคลัง
โทนสีเขียวของUltra ERP
มีหน้าจอ รับสินค้า เบิกสินค้า โอนสินค้า การปรับปรุงสินค้า
มีรายงานสรุปแต่ละหน้าจอที่ทำรายการ
มีหน้าจอกำหนดรายละเอียดสินค้า ใส่รูป ใส่บาร์โค๊ดได้
มีหน้าจอแสดงสินค้าที่อยู่ในแต่ละจังหวัด อ้างอิงแผนที่จาก google map
มีการพิมพ์รายงานการตรวจนับสินค้า
มีกราฟสรุปปริมาณขึ้นลงคงเหลือ
มีหน้าจอกำหนดที่เก็บสินค้าแบบเป็นภาพ ระบุตำแหน่งที่เก็บได้ (คลัง 1 คลัง 2 ...)
มีหน้าจอขายสินค้าแบบ POS ยิงบาร์โค๊ดได้ มีภาพสินค้า พิมพ์ใบเสร็จรับเงินได้
มี Chat bot ใช้ Gemini เป็นผู้ช่วยที่มีความรู้เกี่ยวกับเว็บนี้
ติดตั้งเป็นแอปบนเครื่องได้ (PWA)


# การเข้าสู่ระบบ  (เดิม: รหัส Fixed admin/admin888 — เปลี่ยนแล้ว 2026-08-28)
ใช้ Supabase Auth แบบ อีเมล + รหัสผ่าน
เชื่อมด้วย Project URL + anon (public) key เท่านั้น
สร้างผู้ใช้ที่ Supabase Dashboard > Authentication > Users (ต้องติ๊ก Auto Confirm User)
ระบบไม่มีหน้าสมัครสมาชิก

 # Feature
 - Login ด้วยอีเมล + รหัสผ่าน ผ่าน Supabase Auth
 - ข้อมูลสินค้าคงคลังเก็บบน Supabase Database (แชร์ทุกเครื่อง)
 - ผังที่เก็บสินค้าแบบเป็นภาพ (โซน/ช่องเก็บ) ระบุว่าสินค้าอยู่ช่องไหน
 - ทะเบียนลูกค้า: รหัส ชื่อ ที่อยู่แยกตำบล/อำเภอ/จังหวัด เบอร์โทร ประเภท
 - กำหนดคลังและที่เก็บแบบตาราง (เพิ่ม/แก้ไข/ลบ) แยกจากหน้าผังที่เก็บ
 - กำหนดกลุ่มเอกสาร: ตั้งรูปแบบเลขที่เอกสารรันนิ่งของแต่ละหน้าจอทำรายการ
 - ขายหน้าร้าน POS: ยิงบาร์โค๊ด / คีย์รหัส / กดเลือก + ออกใบเสร็จรับเงิน
 - ผู้ช่วย AI (Gemini): ปุ่มลอยมุมขวาล่าง ตอบเรื่องวิธีใช้งานและข้อมูลในคลังปัจจุบัน
 - ติดตั้งเป็นแอปได้ (PWA) เปิดจากหน้าจอโฮมโดยไม่มีแถบเบราว์เซอร์


 # Deployment
- ใช้ Vercel + NextJS
- ไม่ต้องติดตั้งอะไรทั้งสิ้น (ในเครื่องผู้ใช้)

  วิธีที่ทำ: Vercel จะรัน `npm install` และ `next build` ให้เองบนคลาวด์
  ผู้ใช้ไม่ต้องติดตั้ง Node.js หรือ npm ในเครื่องเลย แค่ push โค้ดหรือลากโฟลเดอร์ขึ้น Vercel
  (ถ้าอยากรันในเครื่องเองภายหลัง ค่อยใช้ `npm install` แล้ว `npm run dev`)

- GitHub: git@github.com:actingsubltsuteepatchotasing-dot/InventorySystem.git


# Stack ที่ใช้
- Next.js 15 (App Router) + React 19
- JavaScript ล้วน (ไม่ใช้ TypeScript) เพื่อลดขั้นตอน
- CSS ธรรมดาไฟล์เดียว (app/globals.css) ไม่ใช้ Tailwind / CSS-in-JS
- Supabase (Auth + Postgres) เรียกผ่าน REST ด้วย fetch โดยตรง
- Google Gemini (ผู้ช่วย AI) เรียกผ่าน REST ด้วย fetch โดยตรง
- ไม่มี dependency อื่นเลยนอกจาก next / react / react-dom
  * ไม่ได้ติดตั้ง @supabase/supabase-js — เขียน client เองที่ lib/supabase.js
    (แลกกับการต้องจัดการ refresh token เอง ซึ่งทำไว้แล้ว)
  * ไม่ได้ติดตั้ง @google/generative-ai — เขียน client เองที่ lib/gemini.js
  * ไอคอนทั้งหมด = inline SVG เขียนเอง
  * บาร์โค๊ด = Code 128-B encoder เขียนเอง (lib/barcode.js)
  * กราฟ = inline SVG เขียนเอง (components/Charts.js) ไม่ใช้ Chart.js
  * แผนที่ = Google Maps Embed ผ่าน iframe (ไม่ต้องใช้ API key)


# ตั้งค่าก่อนใช้งาน  (สำคัญ — 3 ขั้นแรกต้องทำก่อน ไม่งั้น login ไม่ได้)

ขั้นที่ 1 — สร้างตารางใน Supabase  (ไฟล์เดียวจบ)
  Supabase Dashboard > SQL Editor > New query
  วางเนื้อหาไฟล์ supabase/schema.sql ทั้งไฟล์ แล้วกด Run
  ไฟล์นี้ทำครบทุกอย่าง: สร้างตาราง 9 ตาราง, ฟังก์ชัน 2 ตัว, GRANT, RLS,
  รีเฟรช schema cache และแสดงตารางสรุปผลท้ายไฟล์
  ดูคอลัมน์ "ผล" ต้องขึ้น "ผ่าน" ครบทุกแถว
  (รันซ้ำได้ปลอดภัย ไม่ลบข้อมูลเดิม)

ขั้นที่ 2 — สร้างผู้ใช้
  Authentication > Users > Add user
    Email    : อีเมลที่ต้องการ (เช่น admin@example.com)
    Password : ตั้งรหัสที่ปลอดภัย
    ☑ Auto Confirm User   <- ต้องติ๊ก ไม่งั้นจะติด "Email not confirmed"

ขั้นที่ 3 — ใส่ค่า environment
  หาค่าที่ Project Settings > API
    Project URL              -> NEXT_PUBLIC_SUPABASE_URL
    Project API keys > anon  -> NEXT_PUBLIC_SUPABASE_ANON_KEY

  ตอน deploy : Vercel > Project Settings > Environment Variables
               ใส่ทั้งสองค่า แล้ว Redeploy หนึ่งครั้ง
               (ตัวแปร NEXT_PUBLIC_ ถูกฝังตอน build จึงต้อง build ใหม่)
  ตอนรันในเครื่อง : คัดลอก .env.local.example เป็น .env.local แล้วใส่ค่า

  หมายเหตุ: anon key เป็น public key เปิดเผยได้ ความปลอดภัยมาจาก RLS policy
            ห้ามใช้ service_role key ในฝั่ง client เด็ดขาด

ขั้นที่ 4 — ตั้งค่าผู้ช่วย AI  (ไม่บังคับ ข้ามได้ถ้ายังไม่ใช้)
  หาคีย์ฟรีที่ https://aistudio.google.com/apikey
  ใส่ที่ Vercel > Project Settings > Environment Variables แล้ว Redeploy

    GEMINI_API_KEY        <- จำเป็น ถ้าจะใช้ผู้ช่วย AI
    GEMINI_MODEL          <- ไม่บังคับ ค่าเริ่มต้น gemini-2.0-flash
    CHAT_ALLOWED_EMAILS   <- ไม่บังคับ เว้นว่าง = ทุกคนที่ล็อกอินใช้ได้

  *** สำคัญ: GEMINI_API_KEY ต้องไม่มี NEXT_PUBLIC_ นำหน้า ***
  Next.js ฝังเฉพาะตัวแปรที่ขึ้นต้นด้วย NEXT_PUBLIC_ ลงใน JS ที่ส่งให้เบราว์เซอร์
  ถ้าเผลอใส่ คีย์จะหลุดให้ใครก็คัดลอกไปใช้จนโควตาหมด

  ถ้าไม่ตั้งค่า ระบบส่วนอื่นยังใช้ได้ปกติ แค่ผู้ช่วย AI จะบอกว่ายังไม่ได้ตั้งค่า

ขั้นที่ 5 — ตั้งที่อยู่เว็บสำหรับพรีวิวตอนแชร์ลิงก์  (ไม่บังคับ)

    NEXT_PUBLIC_SITE_URL=https://your-app.vercel.app

  ใช้ทำ URL เต็มให้ og:image เพราะ LINE ไม่รับ path แบบสัมพัทธ์
  ถ้า deploy บน Vercel และใช้โดเมนของ Vercel ไม่ต้องใส่ ระบบหยิบให้เอง
  ต้องใส่เมื่อผูกโดเมนของตัวเอง ไม่งั้นการ์ดพรีวิวจะชี้ไปโดเมน Vercel
  ใส่พร้อม https:// และไม่ต้องมี / ปิดท้าย


เมื่อเข้าระบบครั้งแรกและฐานข้อมูลยังว่าง ระบบจะสร้างข้อมูลตัวอย่างให้อัตโนมัติ


# โครงสร้างฐานข้อมูล (supabase/schema.sql)

warehouses         id, code, name, province, lat, lng
products           id, code(unique), name, unit, cat, price, min_qty, barcode, img, note,
                   def_wh_id, def_loc_id  [คลัง/ที่เก็บประจำ ใช้เป็นค่าตั้งต้นบนหน้าจอ]
txns               id, type, doc_no, date, product_id -> products(cascade),
                   qty, wh_id -> warehouses, wh_to -> warehouses,
                   loc_id, loc_to  [ที่เก็บ — foreign key คู่กับ wh_id / wh_to]
                   note, ref, user_name, ts
locations          id, wh_id -> warehouses(cascade), code, name, zone,
                   row_no, col_no, kind, capacity, note      [ช่องเก็บในผังคลัง]
product_locations  id, product_id, location_id, qty          [สินค้าอยู่ช่องไหน]
                   ปรับให้อัตโนมัติทุกครั้งที่บันทึกรายการ ไม่ใช่ข้อมูลที่กรอกเองล้วน ๆ
sales              id, doc_no(unique), date, wh_id, loc_id, customer,
                   subtotal, discount, vat, total, paid, change_amt,
                   pay_method, user_name, note, ts           [หัวบิลขาย]
sale_items         id, sale_id -> sales(cascade), product_id, qty, price, amount
customers          id, code(unique), name, address, subdistrict, district, province,
                   postcode, phone, kind                     [ทะเบียนลูกค้า]
                   ที่อยู่แยกคนละคอลัมน์ เพราะต้องกรองและออกรายงานรายจังหวัด
doc_groups         id (= ชนิดรายการ), name, prefix, period, digits
                   [รูปแบบเลขที่เอกสารของแต่ละหน้าจอทำรายการ]
                   เก็บเฉพาะ "รูปแบบ" ไม่เก็บตัวนับ — ตัวนับที่ฝั่ง client จะไม่ตรงกัน
                   เมื่อใช้ฐานข้อมูลร่วมหลายเครื่อง เลขถัดไปจึงนับจาก txns จริงเสมอ

ฟังก์ชันบนฐานข้อมูล:
  stock_of(p_product, p_wh) -> numeric
    คำนวณยอดคงเหลือของสินค้าหนึ่งในคลังหนึ่ง ใช้กติกาเดียวกับ lib/db.js stockMap

  create_sale(p_sale jsonb, p_items jsonb)
    บันทึก sales + sale_items + txns(SALE) ใน transaction เดียว
    ถ้าล้มกลางทางจะ rollback ทั้งหมด ไม่เหลือบิลที่ไม่ได้ตัดสต็อก
    ก่อนตัดสต็อกจะ pg_advisory_xact_lock คู่ (สินค้า, คลัง) แล้วตรวจยอดคงเหลือ
    ถ้าไม่พอจะ raise exception -> ขายเกินสต็อกไม่ได้แม้ขายพร้อมกันหลายเครื่อง
    ทั้งสองฟังก์ชันเป็น security invoker และตั้ง search_path ชัดเจน

ข้อบังคับที่ตั้งไว้ในฐานข้อมูล (ไม่ใช่แค่ฝั่งหน้าจอ):
  - type ต้องเป็น RECEIVE / ISSUE / TRANSFER / ADJUST / SALE เท่านั้น
  - pay_method ต้องเป็น CASH / TRANSFER / CARD
  - จำนวนที่จัดวางในช่องเก็บ (qty) ต้องไม่ติดลบ
  - จำนวนในรายการขายต้องมากกว่า 0
  - รหัสช่องเก็บห้ามซ้ำภายในคลังเดียวกัน
  - สินค้าหนึ่งรายการอยู่ในช่องเก็บเดียวกันได้แถวเดียว (unique)
  - รายการ TRANSFER ต้องมี wh_to และ wh_to <> wh_id  (กันโอนเข้าคลังตัวเอง)
  - ลบสินค้า -> รายการเคลื่อนไหวที่อ้างถึงถูกลบตาม (on delete cascade)
  - ลบคลังที่ยังมีรายการอ้างอยู่ไม่ได้ (on delete restrict)
  - รหัสลูกค้าห้ามซ้ำ (unique index)
  - รอบการขึ้นเลขเอกสารต้องเป็น none / year / month และจำนวนหลักอยู่ระหว่าง 2-8

การเข้าถึงตารางต้องผ่าน 2 ด่าน (สำคัญ — เคยพลาดตรงนี้)
  ด่าน 1  GRANT ระดับตาราง ให้ role authenticated
          ไม่ผ่าน -> HTTP 403 / SQLSTATE 42501 "permission denied for table"
  ด่าน 2  RLS policy
          ไม่ผ่าน -> อ่านได้ผลว่าง หรือเขียนไม่ได้ ("new row violates ...")

RLS: เปิดทั้ง 9 ตาราง อนุญาตเฉพาะ role = authenticated
     anon key เพียงอย่างเดียวอ่าน/เขียนไม่ได้ ต้อง login ก่อนเสมอ

หมายเหตุชื่อคอลัมน์: ใช้ min_qty และ user_name แทน min / user
เพราะ user เป็นคำสงวนของ SQL — การแปลงชื่อทำที่ lib/api.js

# ช่องกรอกจำนวน มีปุ่มลบ/บวก

ทุกช่องที่กรอก "จำนวน" ใช้คอมโพเนนต์เดียวกัน (QtyInput ใน components/ui.js)
มีปุ่ม − และ + ขนาบสองข้าง กดปรับทีละก้าว หรือพิมพ์ตัวเลขเองก็ได้

ใช้ที่:
  รับ / เบิก / โอนสินค้า   จำนวนที่ทำรายการ
  ปรับปรุงสินค้า           ยอดนับได้จริง (ทุกบรรทัดในตาราง)
  ขายหน้าร้าน POS          จำนวนของแต่ละบรรทัดในบิล (ต่ำสุด 1 เพราะขาย 0 ชิ้นไม่ได้)
  ผังที่เก็บสินค้า          จำนวนที่จะวางลงช่อง, ความจุช่อง (ก้าวละ 100), ลำดับในโซน
  ข้อมูลสินค้า             จุดสั่งซื้อต่ำสุด

ไม่ได้ใส่ให้ช่องที่เป็นจำนวนเงิน (ราคาต่อหน่วย, ส่วนลด, รับเงิน)
เพราะกดทีละ 1 บาทไม่ได้ช่วยอะไร ส่วนช่องรับเงินมีปุ่มลัด +100 / +500 / +1000 / พอดี อยู่แล้ว

รายละเอียดที่ทำไว้:
  - ปล่อยให้ช่องว่างได้ระหว่างพิมพ์ ผู้ใช้จะได้ลบทิ้งแล้วพิมพ์ใหม่
    แต่ตอนกดปุ่มจะนับค่าว่างเป็น 0
  - ปัดเศษหลังบวกลบ กันปัญหาทศนิยมลอยตัว (0.1 + 0.2 ได้ 0.30000000000000004)
  - ถึงค่าต่ำสุด/สูงสุดแล้วปุ่มด้านนั้นถูกปิด
  - ปุ่มเป็น type="button" ไม่งั้นจะไป submit ฟอร์ม
  - ปุ่ม tabIndex -1 กด Tab แล้วข้ามไปช่องถัดไปเลย ไม่ต้องกดผ่านปุ่มสองครั้ง
  - ซ่อนลูกศรของ input number เพราะซ้ำซ้อนกับปุ่มที่ทำเองและเบียดพื้นที่ตัวเลข
  - กล่องมี min-width และช่องกลางลด padding ข้างเหลือ 4px
    รอบแรกลืมจุดนี้ ในเซลล์ตารางแคบ ๆ ปุ่มสองข้าง (34+34) กับ padding ของช่องกรอก (11+11)
    กินพื้นที่จนไม่เหลือที่ให้ตัวเลข เห็นแต่ปุ่มลบกับบวก ตัวเลขหายไปเลย
    คอลัมน์ที่ใส่ช่องจำนวนจึงต้องกว้างพอด้วย มีเทสต์คำนวณให้ว่าเหลือที่ตัวเลขกี่ px


# เลือกสินค้าแบบพิมพ์ค้นหาได้

ทุกหน้าจอที่ให้เลือกสินค้าใช้คอมโพเนนต์เดียวกัน (ProductSelect ใน components/ui.js)
กดเลือกจากรายการก็ได้ พิมพ์ค้นหาก็ได้ ค้นได้จาก รหัส / ชื่อ / บาร์โค๊ด / หมวดหมู่

ใช้ที่: รับสินค้า, เบิกสินค้า, โอนสินค้า, ปรับปรุงสินค้า, ผังที่เก็บสินค้า, รายงาน, กราฟ
(หน้า POS มีช่องค้นหากับการยิงบาร์โค๊ดของตัวเองอยู่แล้ว จึงไม่ได้ใช้ตัวนี้)

ทำไมไม่ใช้ <select> ของเบราว์เซอร์:
  <select> พิมพ์ค้นหาไม่ได้จริง พิมพ์ได้แค่กระโดดตามตัวอักษรแรกเท่านั้น
  พอสินค้าเยอะขึ้นจะเลื่อนหาทีละรายการไม่ไหว

รายละเอียดที่ต้องระวัง:
  - รายการเรนเดอร์ผ่าน portal ไปที่ body และวางตำแหน่งแบบ fixed
    ถ้าเรนเดอร์ในที่เดิมจะถูก overflow ของตาราง (.tbl-wrap) หรือของ modal ตัดหาย
    ต้องคำนวณตำแหน่งใหม่ตอนเลื่อนหน้า (ดัก scroll แบบ capture เพื่อจับกล่องชั้นในด้วย)
  - ที่ด้านล่างไม่พอจะพลิกขึ้นบนให้เอง
  - เลือกด้วย pointerdown + preventDefault ไม่ใช่ click
    ไม่งั้น input เสียโฟกัสก่อน รายการปิดไปแล้วคลิกไม่ติด
  - คลิกนอกกล่องแล้วปิด ต้องเช็คทั้งช่องกรอกและตัวรายการ เพราะอยู่คนละที่ในหน้าเว็บ
  - คีย์บอร์ด: ลูกศรขึ้น-ลงเลื่อน, Enter เลือก, Escape ปิด


# หน้าจอทำรายการแบบตาราง (รับ / เบิก / โอน / ปรับปรุง)

ทุกหน้าจอที่เลือกสินค้ามาทำรายการ กรอกเป็นตารางทีละบรรทัดเหมือนกันหมด
ไม่ต้องกรอกในฟอร์มด้านบนแล้วกด "เพิ่มลงรายการ" ทีละอันอีกต่อไป

ลำดับคอลัมน์:  สินค้า > คลังสินค้า > ที่เก็บสินค้า > จำนวน > (ปลายทางถ้าเป็นการโอน) > หมายเหตุ

กรอกบรรทัดสุดท้ายครบเมื่อไร บรรทัดใหม่ขึ้นให้เองทันที
  รับ/เบิก/โอน   ครบ = เลือกสินค้าแล้วและจำนวนมากกว่า 0
  ปรับปรุงสินค้า  ครบ = เลือกสินค้าแล้วและกรอกยอดนับได้จริงแล้ว (ยอดตรงกับบัญชีก็นับว่ากรอกแล้ว)
บรรทัดใหม่ใช้คลัง/ที่เก็บต่อจากบรรทัดก่อนหน้า เพราะปกติทำเอกสารเดียวคลังเดียว
ส่วนเลือกสินค้าที่มีค่าประจำ บรรทัดนั้นจะเด้งไปตามค่าประจำแทน

การตรวจของไม่พอ นับรวมทั้งตาราง ไม่ใช่ดูทีละบรรทัด
  ถ้าสองบรรทัดหยิบสินค้าเดียวกันจากช่องเดียวกัน ต้องรวมกันแล้วจึงเทียบกับของที่มี
  ตัวเลข "หยิบได้" ใต้ช่องจำนวนก็หักของที่บรรทัดอื่นจองไว้แล้วเช่นกัน
  ไม่งั้นจะดูเหมือนพอทั้งคู่ แล้วไปพังตอนกดบันทึก

ตรวจทั้งตารางก่อนบันทึกแล้วรายงานข้อแรกที่เจอ
  เลือกสินค้าครบไหม / คู่คลัง+ที่เก็บถูกไหม / โอนเข้าคลังหรือช่องเดิมไหม /
  บรรทัดซ้ำกันไหม / ของในช่องพอไหม


# หน้าจอปรับปรุงสินค้าแบบตาราง

กรอกทีละบรรทัดในตารางเดียว ไม่ต้องกรอกในฟอร์มด้านบนแล้วกด "เพิ่มลงรายการ" ทีละอัน

แต่ละบรรทัดมี: สินค้า · คลัง · ที่เก็บ · ยอดตามบัญชี · คงเหลือทั้งคลัง ·
               ยอดนับได้จริง · ผลต่าง · สาเหตุ  (ครบเท่าฟอร์มเดิมทุกช่อง)

  เพิ่มบรรทัด    ใช้คลัง/ที่เก็บต่อจากบรรทัดก่อนหน้า เพราะปกตินับทีละช่องจนจบ
  เลือกสินค้า    ถ้าสินค้ามีคลัง/ที่เก็บประจำ บรรทัดนั้นจะเด้งไปตามค่าประจำให้
  บันทึก         ข้ามบรรทัดที่ยอดตรงกับบัญชีให้เอง แล้วบอกว่าข้ามไปกี่บรรทัด
                 ใบตรวจนับจริงมีบรรทัดที่ตรงเยอะกว่าบรรทัดที่ต่าง จึงไม่ควรบังคับให้ลบทิ้งเอง

ยอดตามบัญชีกับผลต่างคำนวณสดตอนแสดงผล ไม่เก็บค้างไว้ในแถว
ถ้าเก็บไว้ พอมีคนอื่นบันทึกรายการเข้ามาระหว่างที่กำลังกรอก ตัวเลขในตารางจะค้างอยู่กับของเก่า

ตรวจก่อนบันทึกทั้งตารางทีเดียว แล้วรายงานข้อแรกที่เจอ
(เลือกสินค้าครบไหม / คู่คลัง+ที่เก็บถูกไหม / ยอดนับเป็นตัวเลขไม่ติดลบไหม /
 สินค้าซ้ำในที่เก็บเดียวกันภายในเอกสารไหม)


# ธีมสีของโปรแกรม

เลือกได้ 3 โทนจากปุ่มวงกลมสามสีบนแถบบน: เขียว (เริ่มต้น) / ฟ้า / ม่วง

เก็บค่าไว้ใน localStorage ของเครื่องนั้น (key: ultra-theme) ไม่ได้เก็บบนฐานข้อมูล
แต่ละคนจึงเลือกสีของตัวเองได้โดยไม่กระทบคนอื่น

ทำงานยังไง:
  ตั้ง data-theme บน <html> แล้ว CSS ทับเฉพาะโทนแบรนด์กับสีพื้น
  ธีมเขียวคือค่าใน :root อยู่แล้ว จึงไม่ต้องตั้ง attribute

  ทับ:     --brand --brand-d --brand-l --brand-50 --brand-100 --accent
           --bg --surface-2 --fg --fg-muted --fg-faint --border --border-strong --shadow
  ไม่ทับ:  --ok --warn --err --info
           สีสื่อความหมายต้องอ่านได้เหมือนกันทุกธีม ไม่งั้นสีเตือนจะสื่อความหมายเพี้ยน

กันจอกะพริบ:
  สคริปต์สั้น ๆ ต้น <body> อ่าน localStorage แล้วตั้ง data-theme ก่อนเบราว์เซอร์วาดครั้งแรก
  ถ้ารอ useEffect จะเห็นสีเขียวแวบหนึ่งก่อนเปลี่ยนเป็นสีที่เลือกไว้
  ส่วน ThemeProvider อ่าน localStorage ใน useEffect เพราะอ่านตอน render จะพัง server render

กราฟกับโลโก้:
  เดิม hardcode สีเขียวไว้ใน props เปลี่ยนมาส่ง var(--brand) / var(--brand-l) แทน
  SVG รับ CSS variable ได้ทั้ง fill และ stroke จึงเปลี่ยนตามธีมได้เอง
  มีเทสต์กวาดหาสีเขียวคงที่ที่หลงเหลือ ทั้งใน CSS และในไฟล์ components


# แดชบอร์ด — ช่วงวันที่

เลือกช่วงด้วยปฏิทิน "ตั้งแต่วันที่" กับ "ถึงวันที่" พร้อมปุ่มลัด
วันนี้ / เดือนนี้ / 3 เดือน / 6 เดือน / 12 เดือน (ค่าเริ่มต้น 6 เดือนล่าสุด)

สิ่งที่คิดตามช่วงที่เลือก:
  ยอดคงเหลือรวม        คิด ณ วันสิ้นสุดของช่วง ไม่ใช่ ณ วันนี้เสมอไป
                       เลือกช่วงย้อนหลังแล้วจะเห็นภาพ ณ ตอนนั้นจริง ๆ
  สินค้าต่ำกว่าเกณฑ์    ใช้ยอด ณ วันสิ้นสุดเหมือนกัน และตารางก็โชว์ยอดวันเดียวกัน
                       (เดิมตารางโชว์ยอดวันนี้ ซึ่งไม่ตรงกับเหตุผลที่ติดรายการ)
  รายการเคลื่อนไหว      นับเฉพาะในช่วง แทน KPI เดิมที่นับเฉพาะวันนี้
  กราฟรับเข้า-จ่ายออก   แกนเดือนมาจากช่วงที่เลือก จำกัดที่ 24 เดือนล่าสุดของช่วง
                       ไม่งั้นช่วงยาว ๆ จะได้แท่งเล็กจนอ่านไม่ออก
  ยอดรายจังหวัด        ณ วันสิ้นสุดของช่วง

เบื้องหลัง:
  stockMap(db, untilISO) รับวันสิ้นสุดเพิ่มเข้ามา ถ้าไม่ส่งก็ทำงานเหมือนเดิมทุกอย่าง
  monthsBetween(from, to, max) ใน lib/format.js สร้างแกนเดือน
  ช่องวันเริ่มต้นตั้ง max ไว้ที่วันสิ้นสุด และช่องวันสิ้นสุดตั้ง min ไว้ที่วันเริ่มต้น
  ถ้ายังกรอกสลับกันได้ จะขึ้นข้อความเตือนแทนการแสดงตัวเลขมั่ว ๆ


# คลังสินค้ากับที่เก็บ ต้องไปด้วยกันตลอด

กติกาหลักของระบบตั้งแต่รุ่นนี้: **หน้าจอไหนให้เลือกคลัง หน้าจอนั้นต้องให้เลือกที่เก็บด้วย**
และที่เก็บที่เลือกต้องเป็นช่องที่อยู่ในคลังนั้นจริง

ทำไมต้องทำ:
  เดิมรายการเคลื่อนไหวรู้แค่ว่าของอยู่คลังไหน ส่วนผังที่เก็บเป็นข้อมูลที่กรอกเองแยกต่างหาก
  พอทำรายการรับ/เบิก/โอน/ขาย ยอดคงเหลือของคลังขยับ แต่ผังที่เก็บไม่ขยับตาม
  สองอย่างจึงเพี้ยนจากกันทันทีที่ทำรายการแรก และต้องมานั่งไล่แก้เอง

## ที่บังคับไว้ตรงไหนบ้าง

ฐานข้อมูล (supabase/schema.sql)
  txns.loc_id     ที่เก็บที่ของออก/เข้า
  txns.loc_to     ที่เก็บปลายทาง ใช้เฉพาะการโอน
  sales.loc_id    ที่เก็บบนหัวบิลขาย

  บังคับด้วย foreign key คู่ (loc_id, wh_id) -> locations (id, wh_id)
  จึงเป็นไปไม่ได้เลยที่จะบันทึกที่เก็บของคลังหนึ่งลงในรายการของอีกคลังหนึ่ง

  คอลัมน์เป็น null ได้ตั้งใจ เพราะ
    1. ฐานข้อมูลเดิมที่มีข้อมูลอยู่แล้วต้องอัปเกรดผ่าน
    2. ไฟล์สำรอง JSON รุ่นเก่ายังไม่มีที่เก็บ ต้องกู้คืนได้อยู่
  การบังคับกรอกจึงอยู่ที่หน้าจอ ไม่ใช่ที่ constraint

ฝั่งแอป
  lib/db.js       checkWhLoc()  ตรวจคู่ก่อนบันทึกทุกครั้ง
                  binDeltas()   รายการหนึ่งกระทบช่องเก็บไหนบ้าง
                  planPlacementChanges()  แปลงรายการเป็นคำสั่งแก้ผัง + บอกถ้าของไม่พอ
  lib/store.js    addTxns() บันทึกรายการแล้วปรับผังที่เก็บให้ในคราวเดียว
                  ถ้าของในช่องไม่พอจะหยุดตั้งแต่ก่อนเขียนฐานข้อมูล
  components/ui.js  <WhLocFields> คู่ คลัง+ที่เก็บ ที่ใช้ซ้ำทุกหน้าจอ
                    เปลี่ยนคลังแล้วที่เก็บถูกตั้งเป็นช่องแรกของคลังใหม่อัตโนมัติ

## แต่ละหน้าจอเปลี่ยนอะไร

รับสินค้า        เลือกคลัง + ที่เก็บที่จะรับของเข้า
เบิกสินค้า       เลือกคลัง + ที่เก็บที่จะหยิบของออก และตรวจของในช่องนั้น ไม่ใช่ยอดทั้งคลัง
โอนสินค้า        เลือกคู่ทั้งต้นทางและปลายทาง ต้นทางกับปลายทางต้องไม่ใช่ช่องเดียวกัน
ปรับปรุงสินค้า   ตรวจนับทีละช่อง ยอดตามบัญชีคือยอดในช่องนั้น
                 (ทำแบบนี้ผลต่างจะไม่มีทางทำให้ของในช่องติดลบ เพราะยอดใหม่คือยอดที่นับได้จริง)
ขายหน้าร้าน POS  ทุกบรรทัดในบิลบอกช่องที่หยิบของ เลือกช่องที่มีของมากที่สุดให้อัตโนมัติ
                 และเปลี่ยนเองได้จากตารางบิล เปลี่ยนคลังเมื่อไรบิลถูกล้าง
                 เพราะแต่ละบรรทัดผูกกับช่องของคลังเดิม
ผังที่เก็บสินค้า  เลือกที่เก็บจากรายการได้ด้วย ไม่ต้องหาช่องบนผังอย่างเดียว
                 หัวแผงช่องเก็บบอกชื่อคลังกำกับ และมีปุ่ม "ซ่อมผังให้ตรงกับรายการ"
รายงาน           ตัวกรองมี "ที่เก็บ" ต่อจาก "คลังสินค้า" และทุกตาราง/CSV/ใบพิมพ์
                 แสดงเป็น "คลัง · ที่เก็บ"
กราฟ             กรองตามที่เก็บได้ เลือกแล้วกราฟจะเป็นการขึ้นลงของช่องนั้น ไม่ใช่ทั้งคลัง
คลังรายจังหวัด    ตารางคงเหลือบอกด้วยว่าของแต่ละรายการอยู่ช่องไหน จำนวนเท่าไร
ใบตรวจนับ        แยกบรรทัดตามช่องเก็บ เพราะคนเดินนับของนับทีละช่อง
ใบเสร็จ          มีบรรทัด "ที่เก็บ" บนหัวใบเสร็จ

## คลังและที่เก็บประจำของสินค้า

กำหนดได้ที่ฟอร์มสินค้า (สินค้า > แก้ไข) ช่อง "คลังประจำ" และ "ที่เก็บประจำ"
ไม่บังคับ ตั้งหรือไม่ตั้งก็ได้ แต่ถ้าตั้งต้องตั้งทั้งคู่

  products.def_wh_id / def_loc_id
  foreign key คู่ (def_loc_id, def_wh_id) -> locations (id, wh_id)  ที่เก็บต้องอยู่ในคลังนั้น
  check ((def_wh_id is null) = (def_loc_id is null))                ตั้งทั้งคู่หรือไม่ตั้งเลย
  on delete set null                                                ลบช่องเก็บแล้วล้างค่าประจำให้เอง

ตั้งแล้วหน้าจอต่าง ๆ จะเลือกให้อัตโนมัติ:
  รับ / เบิก / โอน   เลือกสินค้า -> คลังต้นทางและที่เก็บต้นทางเด้งไปตามค่าประจำ
  ปรับปรุงสินค้า      เลือกสินค้า -> คลังและที่เก็บเด้งไปตามค่าประจำ
  ขายหน้าร้าน POS    หยิบจากที่เก็บประจำก่อน ถ้าช่องนั้นมีของอยู่
                     ไม่เปลี่ยนคลังให้ เพราะการเปลี่ยนคลังจะล้างบิลทั้งใบ

สินค้าที่ยังไม่ได้ตั้งค่าประจำ จะไม่ไปยุ่งกับคลังที่ผู้ใช้เลือกไว้ (ตั้งใจให้เป็นแบบนั้น)

ลำดับความสำคัญตอนเลือกช่องให้อัตโนมัติ (bestBinFor):
  1. ที่เก็บประจำ ถ้าอยู่ในคลังนี้และมีของอยู่จริง
  2. ช่องที่มีของรายการนี้มากที่สุด
  3. ที่เก็บประจำ ถ้าอยู่ในคลังนี้ (แม้ยังไม่มีของ — ใช้ตอนรับของเข้า)
  4. ช่องแรกของคลัง

defaultBinOf() ตรวจซ้ำทุกครั้งว่าคู่ที่บันทึกไว้ยังใช้ได้จริง ถ้าช่องถูกลบหรือย้ายคลังไปแล้ว
จะคืน null แทนการคืนคู่ที่ใช้ไม่ได้ (จำเป็นเพราะไฟล์สำรองเก่ากู้คืนเข้ามาได้โดยไม่ผ่าน foreign key)

## ผังที่เก็บขยับเองแล้ว

ยอดในช่องเก็บ (product_locations) ไม่ใช่ข้อมูลที่กรอกเองล้วน ๆ อีกต่อไป
ทุกครั้งที่บันทึกรายการ ระบบจะคำนวณผลกระทบต่อช่องเก็บแล้วปรับให้เอง

  RECEIVE / ADJUST เป็นบวก  เพิ่มของในช่อง
  ISSUE / SALE              ลดของในช่อง
  ADJUST เป็นลบ             ลดของในช่อง
  TRANSFER                  ลดที่ช่องต้นทาง เพิ่มที่ช่องปลายทาง

ผลคือ ผลรวมของทุกช่องในคลังหนึ่ง = ยอดคงเหลือของคลังนั้น เสมอ
การจัดวางเองที่หน้าผังยังทำได้อยู่ ไว้ใช้ตอนย้ายของจริงในโกดังโดยไม่มีเอกสาร

ข้อจำกัดที่ยอมรับไว้:
  การบันทึกรายการกับการปรับผังเป็นการเขียน 2 ครั้ง ไม่ได้อยู่ใน transaction เดียว
  (ยกเว้นการขาย ซึ่ง create_sale ทำให้ทั้งก้อนอยู่แล้ว)
  ถ้าเขียนรายการสำเร็จแล้วปรับผังพลาดกลางทาง ผังจะไม่ตรงกับยอดคงเหลือ
  หน้าจอผังที่เก็บจะขึ้นเตือนในการ์ด "สินค้าที่ยังไม่ได้ระบุตำแหน่งครบ"
  และกดปุ่ม "ซ่อมผังให้ตรงกับรายการ" เพื่อคำนวณใหม่จาก txns ทั้งหมดได้

## อัปเกรดฐานข้อมูลเดิม

1. รัน supabase/schema.sql ทั้งไฟล์อีกครั้งใน Supabase SQL Editor
   (เพิ่มคอลัมน์แบบ if not exists รันซ้ำได้ ไม่ลบข้อมูล)
2. เข้าหน้าจอผังที่เก็บสินค้า กด "ซ่อมผังให้ตรงกับรายการ"

รายการเก่าที่บันทึกไว้ก่อนอัปเกรดจะไม่มีที่เก็บ (loc_id เป็น null) ซึ่งตั้งใจให้เป็นแบบนั้น
ของส่วนนั้นจะขึ้นเป็น "ยังไม่ระบุตำแหน่ง" ให้จัดวางเองจากหน้าผัง
ส่วนรายการที่บันทึกใหม่หลังจากนี้จะมีที่เก็บครบทุกใบ

# หน้าจอผังที่เก็บสินค้า (Locations)

แนวคิด: แต่ละคลังมี "ช่องเก็บ" หลายช่อง วางเป็นผังด้วยโซน (แถว) และลำดับ (คอลัมน์)
        เช่น A-01 A-02 A-03 A-04 / B-01 ... / C-01 ...
        ข้อมูลตั้งต้นสร้างให้ 3 โซน × 4 ช่อง = 12 ช่องต่อคลัง (รวม 120 ช่อง)

การใช้งาน:
  - เลือกคลัง แล้วจะเห็นผังเป็นตาราง แต่ละช่องบอกรหัส จำนวนที่เก็บ และแถบระดับความเต็ม
  - สีจุดมุมขวาบนบอกประเภทช่อง: ชั้นวาง / พื้นวางกอง / ห้องเย็น / วัตถุอันตราย
  - คลิกช่อง -> เปิดแผงจัดการ เลือกสินค้าและจำนวน แล้วกด "วางลงช่องนี้"
  - มีตารางแจ้ง "สินค้าที่ยังไม่ได้ระบุตำแหน่งครบ" เทียบยอดคงเหลือกับยอดที่จัดวางแล้ว
  - พิมพ์ผังออกเป็นเอกสารได้

ข้อจำกัดที่ตั้งใจ: การจัดวางเป็น "แผนผังการเก็บ" ไม่ใช่ตัวตัดสินยอดคงเหลือ
ยอดคงเหลือยังคำนวณจาก txns ที่เดียวเสมอ ระบบจะกันไม่ให้วางเกินยอดคงเหลือจริง
และกันไม่ให้เกินความจุของช่อง แต่ถ้ามีการรับ/เบิกภายหลัง ผังจะไม่ขยับตามเอง
ต้องมาปรับเอง (ตารางเตือนด้านล่างจะบอกว่ารายการไหนยังไม่ครบ)


# หน้าจอขายสินค้า POS

เพิ่มสินค้าลงบิลได้ 3 ทาง:
  1. ยิงบาร์โค๊ด  — ช่องรับสแกนโฟกัสอัตโนมัติ เครื่องสแกนทำงานเหมือนแป้นพิมพ์
                    ยิงแล้วกด Enter ระบบเพิ่มสินค้าให้ทันที
  2. คีย์เอง      — พิมพ์บาร์โค๊ดหรือรหัสสินค้า (P001) ในช่องเดียวกันแล้วกด Enter
  3. กดเลือก      — คลิกการ์ดสินค้าที่แสดงรูปภาพ ราคา และยอดคงเหลือ

ฟีเจอร์อื่น:
  - เพิ่มรูปสินค้าได้จากหน้า POS เลย (ปุ่ม "เพิ่มรูป" บนการ์ดที่ยังไม่มีรูป)
  - แก้จำนวนในบิลได้ ส่วนลด VAT 7% คำนวณอัตโนมัติ
  - ปุ่มลัดรับเงิน +100 +500 +1000 และ "พอดี" คำนวณเงินทอนให้
  - กดชำระเงินแล้วพิมพ์ใบเสร็จรับเงินทันที และพิมพ์ซ้ำได้จากรายงาน "บิลขาย / ใบเสร็จ"

การตัดสต็อก: บันทึกบิลแล้วระบบสร้างรายการชนิด SALE ตัดสต็อกทันที
             ยอดคงเหลือจึงมาจาก txns ที่เดียวเหมือนเดิม ไม่มีการนับสองที่
             ระบบตรวจสต็อกทั้งตอนเพิ่มลงบิลและตอนกดชำระเงิน ขายเกินสต็อกไม่ได้

ใบเสร็จ: จัดหน้ากว้าง 78 มม. ใช้ได้ทั้งเครื่องพิมพ์ใบเสร็จความร้อนและกระดาษ A4


## เลขที่บิลและวันที่

วันที่:      เลือกด้วยปฏิทิน ค่าเริ่มต้นเป็นวันนี้ ขายย้อนหลังได้
             ขายวันนี้ลงเวลาจริง ขายย้อนหลังลงเที่ยงวันนั้น
             จะได้เรียงในรายงานถูกและไม่ไปทับรายการอื่น

เลขที่บิล:   ค่าเริ่มต้นเป็นเลขรันนิ่งของวันที่ที่เลือก (SL-YYYYMM-NNNN)
             พิมพ์ทับเองได้ และมีปุ่ม "เลขอัตโนมัติ" กลับไปใช้เลขรันนิ่ง
             เปลี่ยนวันที่แล้วเลขจะวิ่งตามให้ ตราบใดที่ยังไม่ได้พิมพ์ทับ
             ตรวจเลขซ้ำกับบิลที่มีอยู่ก่อนบันทึก (ฐานข้อมูลตั้ง unique ไว้ ซ้ำแล้วบันทึกไม่ผ่าน)
             บันทึกเสร็จจะรีเซ็ตกลับเป็นเลขอัตโนมัติ ไม่ให้เลขที่กรอกเองค้างจนบันทึกซ้ำ

## ลากปรับความกว้างแผงบิล

แถบคั่นระหว่างแคตตาล็อกสินค้ากับแผงบิล ลากด้วยเมาส์ได้ เก็บค่าไว้ใน localStorage
ของเครื่องนั้น (key: ultra-pos-bill-width) เปิดใหม่แล้วได้ความกว้างเดิม

  ลากซ้าย/ขวา     ปรับความกว้าง 320-760px และเหลือที่ให้แคตตาล็อกอย่างน้อย 360px
  ดับเบิลคลิก     คืนค่าเริ่มต้น 430px
  โฟกัสแล้วกดลูกศร ปรับทีละ 16px (กด Shift ค้าง = 48px), Home = คืนค่าเริ่มต้น

ที่ต้องระวังและทำไว้แล้ว:
  - ใช้ setPointerCapture ไม่ได้ผูก listener ที่ window เอง
    ลากออกนอกตัวแถบแล้วยังตามต่อได้ และไม่ค้างเมื่อปล่อยเมาส์นอกหน้าต่าง
  - touch-action: none บนตัวแถบ ไม่งั้นบนแท็บเล็ตจะกลายเป็นการเลื่อนหน้าจอ
  - อ่าน localStorage ใน useEffect เท่านั้น อ่านตอน render จะพังตอน server render
  - จอแคบกว่า 1024px กริดเหลือคอลัมน์เดียว จึงซ่อนแถบคั่น และตอนพิมพ์ก็ซ่อนด้วย

  - รหัสและชื่อต้องไม่ว่าง
  - รหัสห้ามซ้ำ (ตรวจฝั่งหน้าจอเพื่อบอกว่าซ้ำกับใคร + unique index ที่ฐานข้อมูล)
  - รหัสไปรษณีย์ถ้ากรอกต้องเป็นตัวเลข 5 หลัก (เว้นว่างได้)

ค้นหาได้จากทุกช่องพร้อมกัน (รหัส ชื่อ เบอร์โทร ที่อยู่ทุกส่วน) เพราะคนจำคนละอย่างกัน
และกรองตามประเภทลูกค้าได้

ยังไม่ได้ทำ: ช่อง "ชื่อลูกค้า" ที่หน้า POS ยังเป็นข้อความอิสระ ไม่ได้ผูกกับทะเบียนนี้


# กำหนดคลังและที่เก็บ

เมนู การจัดการระบบ > กำหนดคลังและที่เก็บ (components/views/WarehouseSetup.js)

เลือกคลังทางซ้าย แล้วจัดการช่องเก็บของคลังนั้นทางขวา
รวมสองอย่างไว้หน้าจอเดียวเพราะที่เก็บอยู่ลอย ๆ ไม่ได้ ต้องสังกัดคลังเสมอ
(ต่างจากหน้า "ผังที่เก็บสินค้า" ที่เน้นดูเป็นภาพและจัดวางสินค้าลงช่อง)

ตรวจก่อนบันทึกคลัง:
  - รหัส ชื่อ จังหวัด ต้องไม่ว่าง และรหัสคลังห้ามซ้ำ (ใช้อ้างถึงในเอกสารและรายงาน)
  - ละติจูดต้องอยู่ระหว่าง -90 ถึง 90 ลองจิจูด -180 ถึง 180
    ผิดช่วงแล้วหมุดจะหลุดออกนอกแผนที่ในหน้าสินค้าตามจังหวัด

ตรวจก่อนบันทึกช่องเก็บ:
  - รหัสและโซนต้องไม่ว่าง รหัสช่องซ้ำได้ข้ามคลัง แต่ห้ามซ้ำภายในคลังเดียวกัน
  - แถวและช่องที่ต้องเป็นจำนวนเต็มตั้งแต่ 1 ขึ้นไป

กติกาการลบ (เหตุผลเดียวกับข้อ (41) ในบันทึกการแก้ไข):
  - คลังที่ยังมีสินค้าคงเหลือ -> ลบไม่ได้
  - คลังที่เคยมีรายการเคลื่อนไหว -> ลบไม่ได้ (ประวัติต้องเก็บไว้ตรวจสอบย้อนหลัง)
    ฐานข้อมูลตั้ง on delete restrict ไว้อยู่แล้ว แต่กันฝั่งหน้าจอก่อน
    เพราะข้อความจาก Postgres อ่านไม่รู้เรื่อง
  - ลบคลังที่ว่างแล้วแต่ยังมีช่องเก็บ -> ได้ แต่บอกก่อนว่าช่องเก็บจะถูกลบตามไปด้วย
  - ช่องเก็บที่ยังมีของ -> ลบไม่ได้ ต้องย้ายของออกก่อน
    ไม่งั้นผลรวมของทุกช่องจะไม่เท่ากับยอดคงเหลือของคลัง ซึ่งเป็นกติกาที่ทั้งระบบยึดไว้

หมายเหตุ: บิลขายก็สร้างรายการชนิด SALE ใน txns เสมอ การนับ txns จึงครอบคลุมบิลขายด้วย


# กำหนดกลุ่มเอกสาร (เลขที่เอกสารรันนิ่ง)

เมนู การจัดการระบบ > การกำหนดกลุ่มเอกสาร (components/views/DocGroups.js)

ตั้งรูปแบบเลขที่เอกสารของแต่ละหน้าจอทำรายการ:

  ตั้งได้            ค่าเริ่มต้น             ขอบเขต
  อักษรนำหน้า        RC IS TF AD SL         A-Z และ 0-9 ไม่เกิน 6 ตัว
  การขึ้นเลขใหม่     ขึ้นใหม่ทุกเดือน       ต่อเนื่องตลอด / ทุกปี / ทุกเดือน
  จำนวนหลัก          4                      2 ถึง 8

รูปแบบที่ได้:
  ต่อเนื่องตลอด (none)   RC-0001
  ขึ้นใหม่ทุกปี (year)    RC-2026-0001
  ขึ้นใหม่ทุกเดือน (month) RC-202609-0001   <- ค่าเริ่มต้น เท่ากับรูปแบบเดิมของระบบเป๊ะ

หลักการ: ส่วนหน้า (ทุกอย่างก่อนตัวเลขรัน) ทำหน้าที่สองอย่างพร้อมกัน
เป็นทั้งชื่อชุดเอกสาร และเป็นตัวกำหนดรอบที่เลขจะขึ้นต้นใหม่
เพราะเลขรันนับจากเอกสารที่ขึ้นต้นด้วยส่วนหน้าเดียวกันเท่านั้น
period = none จึงคือ "ไม่ใส่ปี/เดือน" แล้วเลขก็วิ่งต่อเนื่องไปเอง

ทำไมไม่เก็บตัวนับ: ฐานข้อมูลใช้ร่วมกันหลายเครื่อง เก็บตัวนับแล้วสองเครื่องอ่านพร้อมกัน
จะได้เลขซ้ำ ระบบจึงหาเลขถัดไปจากเลขสูงสุดที่มีอยู่จริงใน txns เสมอ (nextDocNo ใน lib/db.js)
ตาราง doc_groups บอกแค่ว่าส่วนหน้าหน้าตาเป็นอย่างไร

ตรวจก่อนบันทึก:
  - อักษรนำหน้าห้ามว่าง และใช้ได้เฉพาะ A-Z 0-9 ไม่เกิน 6 ตัว
    (เลขที่เอกสารถูกเอาไปใส่ในชื่อไฟล์และ URL ด้วย)
  - จำนวนหลัก 2-8 ตรงกับ constraint ของฐานข้อมูล
  - อักษรนำหน้าห้ามซ้ำกับกลุ่มอื่นที่ใช้รอบเดียวกัน
    ไม่งั้นสองชนิดรายการจะนับเลขปนกัน แล้วเลขกระโดดข้ามโดยไม่มีสาเหตุที่มองเห็น

เปลี่ยนรูปแบบแล้วเลขเริ่มนับหนึ่งใหม่ — ไม่ใช่บั๊ก แต่เป็นผลโดยตรงจากวิธีนับข้างต้น
พอส่วนหน้าเปลี่ยน เอกสารเก่าก็ไม่ถูกนับด้วย ระบบจะถามยืนยันก่อนถ้ากลุ่มนั้นมีเอกสารอยู่แล้ว
พร้อมบอกว่าเลขถัดไปจะเป็นอะไร (เอกสารเดิมไม่ถูกแก้ไข ยังค้นหาได้ตามปกติ)

ชนิดรายการเพิ่ม/ลบเองไม่ได้ เพราะกลุ่มต้องผูกกับหน้าจอทำรายการหนึ่งต่อหนึ่ง
ชนิดที่ยังไม่เคยบันทึกจะแสดงค่าเริ่มต้นเดิมของระบบ พร้อมป้ายว่า "ยังไม่ได้ตั้งค่า"


# แถบเมนูซ้าย — หุบเป็นกลุ่มได้

กดที่หัวข้อกลุ่มเพื่อหุบกลุ่มนั้น จำสถานะไว้ใน localStorage (ultra-nav-folded)

เก็บเป็น "รายชื่อกลุ่ม" ไม่ใช่หมายเลขลำดับ เพราะลำดับกลุ่มเปลี่ยนได้เมื่อเพิ่มเมนูใหม่
แล้วจะไปหุบผิดกลุ่ม

ซ่อนด้วย attribute hidden ไม่ใช่แค่ CSS เพื่อให้ screen reader ข้ามไปด้วย
และหัวข้อกลุ่มเป็น <button> จริง มี aria-expanded / aria-controls

ไปหน้าที่อยู่ในกลุ่มที่หุบไว้ (เช่นกดทางลัดจากแดชบอร์ด) กลุ่มนั้นจะกางออกให้เอง
ไม่งั้นเมนูจะไม่มีอะไรไฮไลต์เลย คนใช้จะงงว่าตัวเองอยู่ตรงไหน


# ผู้ช่วย AI (Chatbot ด้วย Gemini)

หน้าตา: ปุ่มลอยมุมขวาล่าง เปิดได้จากทุกหน้าจอ กดแล้วเป็นแผงแชท
        บนมือถือแผงจะเต็มจอ ปุ่มและแผงซ่อนอัตโนมัติตอนพิมพ์เอกสาร (.no-print)

ตอบอะไรได้:
  - วิธีใช้งานระบบ เช่น "โอนสินค้าระหว่างคลังทำยังไง"
  - ข้อมูลในคลังตอนนี้ เช่น "สินค้าไหนใกล้หมด" "คลังหาดใหญ่มีน้ำยางข้นเหลือเท่าไร"
  - AI ตอบอย่างเดียว แก้ไขข้อมูลหรือบันทึกรายการให้ไม่ได้ (ตั้งใจออกแบบไว้แบบนั้น)
  - บทสนทนาไม่ถูกบันทึก ปิดหน้าต่างแล้วหายไป

ลำดับการตรวจใน POST /api/chat (ลำดับสำคัญ):
  1. ตรวจ token กับ Supabase
  2. ตรวจ CHAT_ALLOWED_EMAILS
  3. ตรวจว่าตั้ง GEMINI_API_KEY แล้วหรือยัง  <- ต้องอยู่ก่อนข้อ 4
  4. ตรวจโควตา (8/นาที 80/วัน)
  5. ตรวจขนาด payload
  6. เรียก Gemini

  เหตุผลที่ข้อ 3 ต้องมาก่อนข้อ 4: ถ้าสลับกัน ผู้ใช้จะเผาโควตา 8 ครั้งทิ้ง
  ไปกับปัญหาที่ไม่ใช่ความผิดเขา แล้วครั้งที่ 9 ได้ข้อความ "ถามถี่เกินไป"
  ซึ่งชี้ผิดทางสิ้นเชิง (มีเทสต์ดักไว้แล้ว)

GET /api/chat — เช็คว่าพร้อมใช้หรือยัง ใช้ตอนเปิดแผงแชท
  ไม่เรียก Gemini และไม่นับโควตา คืน { configured, allowed }
  ทำให้ผู้ใช้เห็นทันทีตอนกดปุ่มว่ายังไม่ได้ตั้งค่า ไม่ต้องพิมพ์คำถามก่อนถึงจะรู้

เส้นทางข้อมูล:
  ChatWidget สร้างสรุปจาก db ในหน่วยความจำ (ไม่ยิง Supabase ซ้ำ)
    -> POST /api/chat พร้อม Authorization: Bearer <token ของผู้ใช้>
      -> route ตรวจ token กับ Supabase, ตรวจ CHAT_ALLOWED_EMAILS, ตรวจโควตา, ตรวจขนาด
        -> เรียก Gemini REST พร้อม systemInstruction 3 ส่วน (คู่มือ / guardrail / ข้อมูล)
          -> คืนเฉพาะข้อความคำตอบกลับมา

ความปลอดภัย:
  - GEMINI_API_KEY อยู่ฝั่งเซิร์ฟเวอร์เท่านั้น เบราว์เซอร์ไม่เคยเห็น
    ส่งคีย์ทาง header x-goog-api-key ไม่ใช่ query string (กันคีย์โผล่ใน log)
  - ต้องล็อกอินแล้วเท่านั้นจึงเรียก /api/chat ได้ (ยืนยัน token กับ Supabase, cache 60 วินาที)
  - โควตา 8 คำถาม/นาที และ 80 คำถาม/วัน ต่อผู้ใช้
    ข้อจำกัด: เก็บใน memory ของ instance เดียว Vercel มีหลาย instance และ cold start
    จะรีเซ็ตค่า จึงกันสแปมเบา ๆ ไม่ใช่โควตาแม่นยำ
  - ไม่ส่งข้อความ error ดิบจาก Google กลับไปหา client (อาจมีรายละเอียดคีย์/โปรเจกต์)
    ดูของจริงได้ที่ Vercel > Logs
  - lib/appKnowledge.js และ lib/gemini.js ห้าม import จาก client component
    ไม่งั้นคู่มือ ~10 KB จะติดไปกับ JS ที่ผู้ใช้โหลด

ข้อมูลที่ส่งให้ Google (ประมาณ 4.6 KB / 97 บรรทัด ต่อคำถาม):
  ภาพรวม, ตารางสินค้า 12 รายการ, ตารางคลัง 10 แห่ง, เมทริกซ์ยอดคงเหลือ 12x10,
  สินค้าต่ำกว่าจุดสั่งซื้อ, เคลื่อนไหวเดือนนี้/เดือนก่อน, แนวโน้ม 6 เดือน,
  ยอดขายและวิธีชำระ, สินค้าขายดี 5 อันดับ, เคลื่อนไหวล่าสุด 10 รายการ, สรุปผังที่เก็บ

  ไม่ส่ง: รายการเคลื่อนไหวดิบทั้งหมด, รายการในบิลทั้งหมด, รูปภาพสินค้า
  (รูปเป็น data URL หลายสิบ KB ถ้าเผลอส่งจะทำให้คำขอใหญ่มาก จึงเลือก field ทีละตัวเสมอ)

การกัน prompt injection:
  ชื่อสินค้า หมายเหตุ ชื่อลูกค้า เป็นข้อความที่ผู้ใช้พิมพ์เองแล้วถูกยัดเข้า prompt
  ป้องกันสองชั้น:
    1. clean() ตัดขึ้นบรรทัดใหม่ | ` และคำปิดบล็อก <<< DATA>>> แล้วตัดที่ 60 ตัวอักษร
    2. ครอบข้อมูลด้วย <<<DATA ... DATA>>> พร้อมประโยคกำกับว่าเป็นข้อมูลอ้างอิง
       ห้ามทำตามคำสั่งที่อยู่ข้างใน
  ความเสี่ยงจำกัดอยู่แล้วเพราะ AI ไม่มี tool และแก้ข้อมูลไม่ได้ ผลกระทบสูงสุดคือคำตอบเพี้ยน

หมายเหตุเรื่องโมเดล:
  ค่าเริ่มต้น gemini-2.0-flash เหมาะกับโควตาฟรี
  ถ้าตั้ง GEMINI_MODEL เป็น gemini-2.5-* ระบบจะตั้ง thinkingConfig.thinkingBudget = 0
  และเพิ่ม maxOutputTokens เป็น 2048 ให้อัตโนมัติ
  (ไม่งั้น thinking token จะกินโควตาคำตอบจนได้ข้อความว่างพร้อม finishReason MAX_TOKENS)


# พรีวิวตอนแชร์ลิงก์ (Open Graph)

เวลาส่งลิงก์เว็บใน LINE, Facebook หรือ X จะขึ้นการ์ดพรีวิวพร้อมรูป ชื่อ และคำอธิบาย
แทนที่จะเป็นลิงก์เปล่า ๆ

ประกาศไว้ที่ app/layout.js ใน metadata.openGraph และ metadata.twitter
Next.js จะแปลงเป็น meta tag ใน <head> ให้เองตอน render ฝั่งเซิร์ฟเวอร์

  og:title        ระบบควบคุมสินค้าคงคลัง | Ultra ERP
  og:description  รับ / เบิก / โอน / ปรับปรุงสินค้า พร้อมรายงานและกราฟสรุป
  og:image        /og-image.png  (1200x630)
  og:type         website
  og:locale       th_TH
  twitter:card    summary_large_image

*** ข้อสำคัญ: LINE อ่านเฉพาะ og:* ไม่อ่าน twitter:* ***
og:image ต้องเป็น URL เต็มพร้อมโดเมน ใส่ path สัมพัทธ์อย่าง /og-image.png ไม่ได้
Next.js จะเติมโดเมนให้จาก metadataBase ซึ่งหามาจากลำดับนี้ (ฟังก์ชัน siteUrl):

  1. NEXT_PUBLIC_SITE_URL                 ตั้งเองเมื่อผูกโดเมนของตัวเอง
  2. VERCEL_PROJECT_PRODUCTION_URL        โดเมน production ที่ Vercel ให้ คงที่
  3. VERCEL_URL                           โดเมนของ deploy นั้น เปลี่ยนทุกครั้ง
  4. http://localhost:3000                ตอน dev

ถ้าตกไปถึงข้อ 4 บน production พรีวิวจะพัง เพราะครอว์เลอร์โหลดรูปจาก localhost ไม่ได้

รูปการ์ด:
  สร้างด้วย tools/make-og-image.ps1 จากภาพเดียวกับไอคอน (components/fav/ERP.jpg)
  วางเป็นรูปซ้าย + ข้อความขวา พร้อมแถบเขียว บน-ล่าง
  ให้การ์ดยังดูเป็นของ แม้ตัวภาพจะเป็นโทนม่วง

      powershell -ExecutionPolicy Bypass -File tools/make-og-image.ps1

  สคริปต์นี้ต้องบันทึกเป็น UTF-8 with BOM เท่านั้น
  PowerShell 5.1 อ่านไฟล์ที่ไม่มี BOM เป็น ANSI ข้อความไทยที่วาดลงรูปจะเพี้ยนทั้งหมด
  (ต่างจาก make-icons.ps1 ที่มีไทยแค่ในคอมเมนต์จึงไม่เป็นไร)

  เลือกฟอนต์ไทยจากที่มีในเครื่องตามลำดับ Leelawadee UI > Leelawadee > Tahoma
  และย่อขนาดฟอนต์ลงอัตโนมัติจนข้อความพอดีกรอบ

ข้อควรรู้:
  - หน้าเว็บต้องล็อกอินก็จริง แต่ meta tag อยู่ใน layout ซึ่ง render ฝั่งเซิร์ฟเวอร์เสมอ
    ครอว์เลอร์จึงอ่านได้โดยไม่ต้องล็อกอิน และ /og-image.png เป็นไฟล์ static เข้าถึงได้ตรง
  - LINE แคชผลพรีวิวไว้ ถ้าแก้รูปหรือข้อความแล้วยังเห็นของเก่า
    ให้ลองแชร์ลิงก์ที่ต่อ ?v=2 ท้าย URL เพื่อบังคับให้ดึงใหม่
  - ยังไม่ได้ทดสอบกับ LINE จริง ต้อง deploy ก่อนถึงจะลองได้


# ติดตั้งเป็นแอป (PWA)

ประกอบด้วย 3 ส่วนตามข้อกำหนดของเบราว์เซอร์:
  1. Web App Manifest — app/manifest.js
  2. ไอคอน PNG จริง — public/icons/ (192, 512, maskable 512)
  3. Service Worker ที่มี fetch handler — public/sw.js

วิธีติดตั้ง:
  Android Chrome / Windows / macOS : กดปุ่ม "ติดตั้งแอป" บนแถบด้านบน
                                     (ปุ่มโผล่เฉพาะตอนเบราว์เซอร์พร้อม และหายเองหลังติดตั้ง)
  iPhone / iPad Safari             : ปุ่มแชร์ > เพิ่มไปยังหน้าจอโฮม
                                     (iOS ไม่รองรับ beforeinstallprompt จึงไม่มีปุ่มในหน้าเว็บ)

ไอคอน:
  ต้นฉบับ: components/fav/ERP.jpg (554x554)
  สร้างด้วย tools/make-icons.ps1 ซึ่งใช้ System.Drawing ที่มากับ Windows
  จึงไม่ต้องติดตั้ง sharp หรือ canvas และไม่เพิ่ม dependency

      powershell -ExecutionPolicy Bypass -File tools\make-icons.ps1 -CropX 77 -CropY 77 -CropSize 400

  ได้ไฟล์ 6 ไฟล์: public/icons/{icon-192, icon-512, icon-maskable-512}.png
                 app/{icon, apple-icon}.png และ app/favicon.ico

  ทำไมต้องครอป 400 จาก 554:
    ภาพต้นฉบับเป็นอินโฟกราฟิก มีกล่องไอคอนย่อยล้อมรอบคำว่า ERP
    ถ้าย่อทั้งภาพลงเหลือ 32px (ขนาดจริงบนแท็บเบราว์เซอร์) จะกลายเป็นก้อนสีอ่านไม่ออก
    ครอปเหลือ 400 ทำให้ตัวอักษร ERP ใหญ่พอจะอ่านออกที่ 32px
    โดยยังเห็นองค์ประกอบรอบ ๆ เกือบครบตอนแสดงขนาดใหญ่
    (ทดลองเทียบ 320/400/460/531 แล้ว 400 ให้ผลดีที่สุดทั้งสองขนาด)

  ตัวเลือกอื่นของสคริปต์:
    ไม่ใส่อะไรเลย  ตัดขอบขาวรอบภาพอัตโนมัติแล้วใช้ทั้งภาพ
    -NoTrim        ใช้ทั้งภาพตามเดิมไม่ตัดอะไร
    -Source <path> เปลี่ยนไฟล์ต้นฉบับ

  favicon.ico — ไอคอนบนแท็บเบราว์เซอร์:
    ทำไมต้องมีแยกจาก icon.png ทั้งที่ Next.js ใช้ icon.png เป็น favicon ให้อยู่แล้ว
      icon.png มีขนาดเดียวคือ 192px แล้วปล่อยให้เบราว์เซอร์ย่อลง 16/32 เอง
      ผลที่ได้เบลอกว่าการเรนเดอร์ที่ขนาดนั้นตรง ๆ มาก โดยเฉพาะภาพที่มีตัวอักษร
      ico เก็บภาพที่เรนเดอร์แยกตามขนาดไว้ เบราว์เซอร์หยิบอันที่พอดีไปใช้เลย
      และ /favicon.ico เป็น path ที่เบราว์เซอร์ขอเองอยู่แล้วแม้ไม่มี <link>

    ใช้กรอบครอปคนละอันกับไอคอนแอป: 250 แทน 400 (จุดกึ่งกลางเดียวกัน)
    เพราะที่ 16px ถ้าครอป 400 จะเห็นเป็นก้อนสีล้วน ๆ อ่านคำว่า ERP ไม่ออกเลย
    ครอป 250 ทำให้ตัวอักษรเต็มกรอบพอจะอ่านออกที่ 32/48px และยังพอเดาออกที่ 16px
    เปลี่ยนได้ด้วย -FaviconCrop (ใส่ 0 = ใช้กรอบเดียวกับไอคอนแอป)

    ประกอบไฟล์ ico เองในสคริปต์ เพราะ System.Drawing บันทึก ico หลายขนาดไม่ได้
    โครงสร้าง: ICONDIR 6 ไบต์ + ICONDIRENTRY 16 ไบต์ต่อรูป + เนื้อ PNG ต่อท้าย
    มีเทสต์แกะไฟล์ตรวจ offset ทุกรายการว่าต่อเนื่องและไม่เลยท้ายไฟล์

  ไอคอน maskable เว้นขอบข้างละ 14% ตาม safe zone ไม่งั้น Android จะครอบจนภาพขาด
  มีเทสต์ถอดรหัส PNG ระดับพิกเซลตรวจว่าทุกมุมทึบและไม่มีเนื้อหาล้ำเข้าขอบ 10%

  ข้อควรรู้เมื่อรันสคริปต์:
    โฟลเดอร์นี้อยู่บน OneDrive ซึ่งจะล็อกไฟล์ที่เพิ่งสร้างไว้ชั่วครู่
    สคริปต์จึงลบไฟล์เดิมก่อนเขียนเสมอ และ throw ทันทีถ้าเขียนไม่สำเร็จ
    (เวอร์ชันแรกไปอ่านขนาดของไฟล์เก่ามารายงานว่า "สำเร็จ" ทั้งที่เขียนไม่ผ่าน)
    ถ้ายังติด Access denied ให้ลบไฟล์ในโฟลเดอร์ public/icons และ app/*.png ทิ้งก่อน

  ถ้าอยากกลับไปใช้โลโก้ใบยาง ที่วาดด้วยโค้ด ให้รัน node tools/make-icons.mjs

  หมายเหตุเรื่องสี:
    ภาพ ERP เป็นโทนม่วง/ชมพู ขณะที่ธีมเว็บและ theme_color เป็นเขียว #00693C
    ไอคอนบนหน้าจอโฮมจึงคนละโทนกับแถบบนของแอป ถ้าต้องการให้เข้าชุดกัน
    ต้องเปลี่ยนภาพต้นฉบับหรือเปลี่ยนสีธีม ซึ่งยังไม่ได้ทำ

Service Worker — กฎที่ห้ามแหก:
  ระบบนี้มีหลายผู้ใช้และข้อมูลอยู่บนฐานข้อมูลกลาง ถ้าแคชผิดจะเสิร์ฟข้อมูลของคนอื่น
  หรือข้อมูลเก่าให้ จึงตั้งกฎไว้ 4 ข้อ และมีเทสต์ดักทุกข้อ:
    1. ข้ามทุกคำขอที่ไม่ใช่ GET
    2. ข้ามคำขอข้ามโดเมน — Supabase และ Gemini ต้องผ่านเน็ตเสมอ
    3. ไม่แตะ /api/ เลย
    4. HTML ใช้ network-first — deploy ใหม่มีผลทันที ไม่ค้างเวอร์ชันเก่า
  แคชเฉพาะไฟล์ที่ชื่อเปลี่ยนตามเนื้อหา (/_next/static/) แบบ cache-first
  และเก็บเฉพาะคำตอบที่ response.ok และ type === "basic"

  *** ใช้งานออฟไลน์ไม่ได้ และไม่ได้ตั้งใจให้ได้ ***
  เน็ตหลุดจะขึ้น public/offline.html พร้อมปุ่มลองใหม่ และเด้งกลับเองเมื่อเน็ตมา

การอัปเดต:
  ตั้ง updateViaCache: "none" ตอนลงทะเบียน ไม่งั้นเบราว์เซอร์อาจใช้ sw.js เก่าจาก cache
  เมื่อมีเวอร์ชันใหม่จะขึ้น toast ให้ปิดแล้วเปิดแอปใหม่
  จงใจไม่ reload อัตโนมัติ เพราะผู้ใช้อาจกำลังคีย์บิลขายค้างอยู่

viewportFit: cover + env(safe-area-inset-*):
  เปิดแบบเต็มจอบนมือถือที่มี notch เนื้อหาจะลอดใต้ขอบได้
  ธาตุลอยมุมขวาล่างทั้งหมด (.user-dock .chat-fab .chat-panel #toasts) จึงบวก
  env(safe-area-inset-bottom/right) เข้าไปด้วย

# ข้อมูลตัวอย่าง (สร้างอัตโนมัติเมื่อฐานข้อมูลว่าง — แก้ไข/ลบได้ทั้งหมด)

  ระวัง: นำเข้าและรีเซ็ตมีผลกับ Supabase จึงกระทบผู้ใช้ทุกคน ไม่ใช่แค่เครื่องตัวเอง

# ข้อจำกัดที่ควรทราบ
- เลขที่เอกสารของ รับ/เบิก/โอน/ปรับปรุง คำนวณฝั่ง client
  ถ้าผู้ใช้ 2 คนกดบันทึกพร้อมกันในรอบเดียวกัน อาจได้เลขซ้ำได้
  (หน้าจอกำหนดกลุ่มเอกสารเปลี่ยนได้แค่ "รูปแบบ" ไม่ได้แก้ข้อจำกัดข้อนี้)
  (ตาราง txns ไม่ได้บังคับ unique บน doc_no)
  ถ้าต้องการกันจริงจัง ให้ย้ายไปออกเลขด้วย Postgres sequence ฝั่งเซิร์ฟเวอร์
  * ยกเว้นบิลขาย (sales) ที่มี unique index บน doc_no แล้ว ถ้าซ้ำจะถูกปฏิเสธ

- การจัดวางสินค้าในผังคลังเป็น "แผนผังการเก็บ" ไม่ใช่ตัวตัดสินยอดคงเหลือ
  ถ้ามีรับ/เบิกภายหลัง ผังจะไม่ขยับตามเอง ต้องมาปรับเอง
  (ตารางเตือนในหน้าจอจะบอกว่ารายการไหนยังระบุตำแหน่งไม่ครบ)
- ข้อมูลถูกโหลดมาทั้งหมดตอนเข้าระบบ เหมาะกับข้อมูลระดับหลักหมื่นแถว
  ถ้าโตกว่านั้นควรเปลี่ยนไปโหลดเฉพาะช่วงที่ดูอยู่
- รูปสินค้าเก็บเป็น data URL ในคอลัมน์ text ถ้ามีรูปเยอะควรย้ายไปใช้ Supabase Storage
- ผู้ใช้ที่ล็อกอินแล้วทุกคนมีสิทธิ์เท่ากันทั้งหมด (อ่าน/เขียน/ลบได้ทุกอย่าง)
  ยังไม่มีระบบแบ่งบทบาท เช่น ผู้ดูแล / เจ้าหน้าที่คลัง / ผู้อ่านอย่างเดียว
- แผนที่ต้องเชื่อมต่ออินเทอร์เน็ต (Google Maps Embed)

  ติดตั้งเป็นแอปได้ก็จริง แต่เปิดแล้วยังต้องมีเน็ต เพราะข้อมูลอยู่บนฐานข้อมูลกลาง
  PWA ที่ทำไว้ช่วยแค่เปิดเร็วขึ้นและมีไอคอนบนหน้าจอโฮม ไม่ได้ทำให้ใช้ออฟไลน์ได้
- ยังไม่มีการยกเลิก/คืนสินค้าจากบิลขาย ถ้าขายผิดต้องใช้หน้าจอปรับปรุงสินค้าแก้ยอดเอง
- ทะเบียนลูกค้ายังไม่ได้ผูกกับหน้า POS ช่อง "ชื่อลูกค้า" ในบิลยังเป็นข้อความอิสระ
  จึงยังออกรายงานยอดขายแยกรายลูกค้าไม่ได้
- ตรวจ SQL ได้แค่เชิงข้อความ ไม่มี PostgreSQL ในเครื่องสำหรับรันจริง
  บั๊กเชิงไวยากรณ์จึงหลุดไปได้ (เคยเกิดจริงกับ %L/%I) ตอนนี้มีเทสต์ดักบางส่วนแล้ว

- ผู้ช่วย AI ส่งสรุปข้อมูลคลัง (~4.6 KB) ไปประมวลผลที่ Google
  ถ้าข้อมูลเป็นความลับระดับที่ส่งออกนอกองค์กรไม่ได้ ต้องปิดฟีเจอร์นี้
  (ไม่ตั้ง GEMINI_API_KEY = ปุ่มยังอยู่แต่ใช้ไม่ได้ หรือถอด <ChatWidget /> ออกจาก Shell.js)

- โควตาผู้ช่วย AI เก็บในหน่วยความจำของ instance เดียว Vercel มีหลาย instance
  และ cold start จะรีเซ็ตค่า จึงกันสแปมเบา ๆ ได้ แต่ไม่ใช่โควตาที่แม่นยำ
  ถ้าต้องการแม่นจริงต้องเก็บลงตารางใน Supabase

- ผู้ช่วย AI อาจตอบผิดได้ ควรตรวจตัวเลขสำคัญกับหน้าจอรายงานอีกครั้งก่อนใช้ตัดสินใจ

- สรุปข้อมูลถูกสร้างที่ฝั่ง client ผู้ใช้ปลอมตัวเลขที่ส่งให้ AI ได้

# ปัญหาที่เคยเจอและวิธีแก้

ผู้ช่วย AI ขึ้นว่า "ไม่พบโมเดล AI ที่ตั้งค่าไว้"

  สาเหตุที่เจอจริง: Google ปลดระวางรุ่นเป็นระยะ และคีย์ที่สร้างใหม่จะเรียกรุ่นเก่าไม่ได้
  ทั้งที่ ListModels ยังรายงานชื่อนั้นอยู่ ข้อความจาก Google จะประมาณว่า
    "This model models/gemini-2.5-flash is no longer available to new users.
     Please update your code to use models/gemini-3.6-flash"

  ระบบจะดึงชื่อรุ่นที่ Google แนะนำมาขึ้นให้เห็นในข้อความ error เลย
  เอาชื่อนั้นไปตั้งเป็น GEMINI_MODEL ที่ Vercel แล้ว Redeploy

  เจอมาแล้ว 2 รอบ (gemini-2.0-flash แล้วก็ gemini-2.5-flash) คาดว่าจะเจออีก
  ไม่ต้องแก้โค้ด แค่เปลี่ยนค่า env ตามที่ข้อความบอก


  Google ตอบ 404 = ชื่อโมเดลนั้นคีย์นี้เรียกไม่ได้ ไม่ใช่บั๊กของเรา
  ชื่อโมเดลของ Google เปลี่ยนและปลดระวางเป็นระยะ และแต่ละคีย์เห็นรายการไม่เท่ากัน

  ดูว่าคีย์ตัวเองใช้อะไรได้ เปิดลิงก์นี้ในเบราว์เซอร์ (แทน YOUR_KEY ด้วยคีย์จริง):
      https://generativelanguage.googleapis.com/v1beta/models?key=YOUR_KEY

  เลือกชื่อที่มี "generateContent" อยู่ใน supportedGenerationMethods
  แล้วตั้ง GEMINI_MODEL ที่ Vercel เป็นชื่อนั้น (ตัดคำนำหน้า "models/" ออก) แล้ว Redeploy

  ตั้งแต่รุ่นนี้ ระบบจะไปขอรายชื่อโมเดลมาต่อท้ายข้อความ error ให้เอง
  จึงเห็นได้จากในแอปเลยว่ามีตัวไหนให้เลือก ไม่ต้องไปเปิดลิงก์ข้างบน
  ถ้าขอรายชื่อไม่ได้ด้วย แปลว่าคีย์ผิดหรือยังไม่ได้เปิดใช้ Generative Language API



อาการ: login ผ่าน แต่ขึ้น "เชื่อมต่อฐานข้อมูลไม่สำเร็จ / ไม่มีสิทธิ์เข้าถึงข้อมูล"
สาเหตุ: schema.sql รุ่นแรกตั้ง RLS policy อย่างเดียว ลืม GRANT ระดับตาราง
วิธีแก้: รัน supabase/schema.sql ทั้งไฟล์ใน SQL Editor แล้วดูตารางสรุปท้ายไฟล์
        คอลัมน์ "ผล" ต้องขึ้น "ผ่าน" ครบทุกแถว
        หรือใช้ปุ่ม "ข้อมูล" > "ตรวจสอบระบบตอนนี้" ในแอป ซึ่งตรวจให้ทีละรายการ

อาการ: ERROR 42601 syntax error at or near "'ชื่อ policy'"
สาเหตุ: ใน DO block ใช้ format('drop policy ... %L ...') กับชื่อ policy
        %L สร้าง string literal (') แต่ชื่อ policy เป็น identifier ต้องใช้ %I (")
        และเพราะ SQL Editor รันทั้งไฟล์เป็น transaction เดียว ทุกอย่างจึง rollback
        ตารางไม่ถูกสร้างเลย ทำให้ตามมาด้วย PGRST205 ตอนเปิดแอป
วิธีแก้: แก้แล้วใน schema.sql (ใช้ %I ทั้งชื่อ policy และชื่อตาราง)
        มีเทสต์ดักไว้แล้วไม่ให้พลาดซ้ำ

อาการ: PGRST205 "Could not find the table 'public.xxx' in the schema cache"
สาเหตุ: 1) ยังไม่ได้รัน schema.sql เวอร์ชันที่มีตารางนั้น หรือ
        2) รันแล้วแต่ PostgREST ยังไม่รีเฟรช schema cache
วิธีแก้: รัน supabase/schema.sql ทั้งไฟล์ (ท้ายไฟล์มี notify pgrst, 'reload schema' แล้ว)
        ถ้ายังไม่หาย ให้รันคำสั่งนี้เดี่ยว ๆ แล้วรอ 5 วินาที:
            notify pgrst, 'reload schema';

        จะปิดเฉพาะหน้าจอนั้นและขึ้นวิธีแก้ให้ ส่วนอื่นใช้งานต่อได้

                - การขายมีกราฟมูลค่ารายเดือนเพิ่มมาอีกอัน ไม่ใช่ดูแค่จำนวนชิ้น

                - ตัวกรองเดิม (ช่วงเวลา สินค้า คลัง ที่เก็บ) ใช้ได้กับทุกแท็บเหมือนเดิม
                - เทสต์เพิ่ม 19 ข้อ รวมถึงตรวจว่าทุกแท็บกราฟมีรายงานคู่กันจริง

           (44) เพิ่มลูกค้า / กลุ่มเอกสาร / กำหนดคลังและที่เก็บ + เมนูหุบเป็นกลุ่มได้
                - ตารางใหม่ 2 ตาราง: customers, doc_groups (รวมเป็น 9 ตาราง)
                  ทั้งคู่เป็น "ตารางของฟีเจอร์ใหม่" ฐานข้อมูลเดิมที่ยังไม่ได้รัน schema

                - รายละเอียดลูกค้า: ที่อยู่แยกตำบล/อำเภอ/จังหวัด/รหัสไปรษณีย์คนละคอลัมน์
                  เพราะต้องเอาไปกรองและออกรายงานรายจังหวัด เก็บรวมเป็นก้อนเดียวแล้วแยกไม่ออก
                  ค้นจากทุกช่องพร้อมกัน (รหัส ชื่อ เบอร์โทร ที่อยู่) เพราะคนจำคนละอย่างกัน

                  (ฝั่งหน้าจอมีเพื่อบอกได้ว่าซ้ำกับ "ใคร" ไม่ใช่แค่บอกว่าซ้ำ)
                - กำหนดกลุ่มเอกสาร: ตั้งอักษรนำหน้า รอบการขึ้นเลขใหม่ และจำนวนหลัก
                  ค่าเริ่มต้นตรงกับรูปแบบเดิมเป๊ะ (RC-202608-0007) เอกสารเก่ากับใหม่
                  จึงยังเป็นชุดเลขเดียวกัน
                  ตารางเก็บเฉพาะ "รูปแบบ" ไม่เก็บตัวนับ เพราะฐานข้อมูลใช้ร่วมหลายเครื่อง
                  เก็บตัวนับแล้วสองเครื่องอ่านพร้อมกันจะได้เลขซ้ำ nextDocNo จึงยังนับจาก
                  เลขสูงสุดที่มีอยู่จริงใน txns เหมือนเดิม
                  ผลข้างเคียงที่ต้องบอกผู้ใช้: เปลี่ยนรูปแบบแล้วเลขเริ่มนับหนึ่งใหม่
                  เพราะเลขนับเฉพาะเอกสารที่ขึ้นต้นด้วยส่วนหน้าเดียวกัน
                  จึงถามยืนยันก่อนพร้อมบอกว่าเลขถัดไปจะเป็นอะไร
                  กันอักษรนำหน้าซ้ำกับกลุ่มอื่นที่ใช้รอบเดียวกัน ไม่งั้นสองชนิดรายการ
                  จะนับปนกันแล้วเลขกระโดดข้ามโดยไม่มีสาเหตุที่มองเห็น
                  nextDocNo ตัดเฉพาะส่วนท้ายที่เป็นตัวเลขล้วนแล้ว เลขรูปแบบเก่าที่ปนอยู่

                - กำหนดคลังและที่เก็บ: เลือกคลังซ้าย จัดการช่องเก็บขวา
                  รวมไว้หน้าเดียวเพราะที่เก็บอยู่ลอย ๆ ไม่ได้ ต้องสังกัดคลังเสมอ
                  กติกาการลบใช้ชุดเดียวกับข้อ (41): คลังที่ยังมีของหรือเคยมีรายการ
                  เคลื่อนไหวลบไม่ได้ ช่องที่ยังมีของลบไม่ได้
                  ฐานข้อมูลตั้ง on delete restrict ไว้แล้วก็จริง แต่กันฝั่งหน้าจอก่อน
                  เพราะข้อความที่ Postgres คืนมาอ่านไม่รู้เรื่อง
                  บิลขายสร้างรายการ SALE ใน txns ด้วย การนับ txns จึงครอบคลุมบิลขายไปในตัว
                - แถบเมนูซ้ายหุบเป็นกลุ่มได้ เก็บเป็นรายชื่อกลุ่มไม่ใช่หมายเลขลำดับ

                  ไม่งั้นเมนูจะไม่มีอะไรไฮไลต์ คนใช้จะงงว่าตัวเองอยู่ตรงไหน
                - หน้าปรับปรุงสินค้าแยกคลังกับที่เก็บเป็นคนละคอลัมน์
                  ให้เรียงเหมือนหน้ารับ/เบิก/โอน ไม่ใช่ซ้อนกันในช่องเดียว
                - เก็บกวาดข้อความที่ผูกกับ "7 ตาราง" ทั้งใน Shell.js, SetupNotice.js,

# Overview
จัดทำโปรแกรมควบคุมสินค้าคงคลัง
โทนสีเขียวของการยางแห่งประเทศไทย
มีหน้าจอ รับสินค้า เบิกสินค้า โอนสินค้า การปรับปรุงสินค้า
มีรายงานสรุปแต่ละหน้าจอที่ทำรายการ
มีหน้าจอกำหนดรายละเอียดสินค้า ใส่รูป ใส่บาร์โค๊ดได้
มีหน้าจอแสดงสินค้าที่อยู่ในแต่ละจังหวัด อ้างอิงแผนที่จาก google map
มีการพิมพ์รายงานการตรวจนับสินค้า
มีกราฟสรุปปริมาณขึ้นลงคงเหลือ
มีหน้าจอกำหนดที่เก็บสินค้าแบบเป็นภาพ ระบุตำแหน่งที่เก็บได้ (คลัง 1 คลัง 2 ...)
มีหน้าจอขายสินค้าแบบ POS ยิงบาร์โค๊ดได้ มีภาพสินค้า พิมพ์ใบเสร็จรับเงินได้

 # Feature
 - Login ด้วยอีเมล + รหัสผ่าน ผ่าน Supabase Auth
 - ข้อมูลสินค้าคงคลังเก็บบน Supabase Database (แชร์ทุกเครื่อง)
 - ผังที่เก็บสินค้าแบบเป็นภาพ (โซน/ช่องเก็บ) ระบุว่าสินค้าอยู่ช่องไหน
 - ขายหน้าร้าน POS: ยิงบาร์โค๊ด / คีย์รหัส / กดเลือก + ออกใบเสร็จรับเงิน

# ตั้งค่าก่อนใช้งาน  (สำคัญ — ทำ 3 ขั้นนี้ก่อน ไม่งั้น login ไม่ได้)

ขั้นที่ 1 — สร้างตารางใน Supabase  (ไฟล์เดียวจบ)
  Supabase Dashboard > SQL Editor > New query
  วางเนื้อหาไฟล์ supabase/schema.sql ทั้งไฟล์ แล้วกด Run
  ไฟล์นี้ทำครบทุกอย่าง: สร้างตาราง 7 ตาราง, ฟังก์ชัน 2 ตัว, GRANT, RLS,
  รีเฟรช schema cache และแสดงตารางสรุปผลท้ายไฟล์
  ดูคอลัมน์ "ผล" ต้องขึ้น "ผ่าน" ครบ 7 แถว
  (รันซ้ำได้ปลอดภัย ไม่ลบข้อมูลเดิม)

ขั้นที่ 2 — สร้างผู้ใช้
  Authentication > Users > Add user
    Email    : อีเมลที่ต้องการ (เช่น admin@raot.local)
    Password : ตั้งรหัสที่ปลอดภัย
    ☑ Auto Confirm User   <- ต้องติ๊ก ไม่งั้นจะติด "Email not confirmed"

ขั้นที่ 3 — ใส่ค่า environment
  หาค่าที่ Project Settings > API
    Project URL              -> NEXT_PUBLIC_SUPABASE_URL
    Project API keys > anon  -> NEXT_PUBLIC_SUPABASE_ANON_KEY

  ตอน deploy : Vercel > Project Settings > Environment Variables
               ใส่ทั้งสองค่า แล้ว Redeploy หนึ่งครั้ง
               (ตัวแปร NEXT_PUBLIC_ ถูกฝังตอน build จึงต้อง build ใหม่)
  ตอนรันในเครื่อง : คัดลอก .env.local.example เป็น .env.local แล้วใส่ค่า

  หมายเหตุ: anon key เป็น public key เปิดเผยได้ ความปลอดภัยมาจาก RLS policy
            ห้ามใช้ service_role key ในฝั่ง client เด็ดขาด

เมื่อเข้าระบบครั้งแรกและฐานข้อมูลยังว่าง ระบบจะสร้างข้อมูลตัวอย่างให้อัตโนมัติ


# โครงสร้างฐานข้อมูล (supabase/schema.sql)

warehouses         id, code, name, province, lat, lng
products           id, code(unique), name, unit, cat, price, min_qty, barcode, img, note
txns               id, type, doc_no, date, product_id -> products(cascade),
                   qty, wh_id -> warehouses, wh_to -> warehouses,
                   note, ref, user_name, ts
locations          id, wh_id -> warehouses(cascade), code, name, zone,
                   row_no, col_no, kind, capacity, note      [ช่องเก็บในผังคลัง]
product_locations  id, product_id, location_id, qty          [สินค้าอยู่ช่องไหน]
sales              id, doc_no(unique), date, wh_id, customer,
                   subtotal, discount, vat, total, paid, change_amt,
                   pay_method, user_name, note, ts           [หัวบิลขาย]
sale_items         id, sale_id -> sales(cascade), product_id, qty, price, amount

ฟังก์ชันบนฐานข้อมูล:
  stock_of(p_product, p_wh) -> numeric
    คำนวณยอดคงเหลือของสินค้าหนึ่งในคลังหนึ่ง ใช้กติกาเดียวกับ lib/db.js stockMap

  create_sale(p_sale jsonb, p_items jsonb)
    บันทึก sales + sale_items + txns(SALE) ใน transaction เดียว
    ถ้าล้มกลางทางจะ rollback ทั้งหมด ไม่เหลือบิลที่ไม่ได้ตัดสต็อก
    ก่อนตัดสต็อกจะ pg_advisory_xact_lock คู่ (สินค้า, คลัง) แล้วตรวจยอดคงเหลือ
    ถ้าไม่พอจะ raise exception -> ขายเกินสต็อกไม่ได้แม้ขายพร้อมกันหลายเครื่อง
    ทั้งสองฟังก์ชันเป็น security invoker และตั้ง search_path ชัดเจน

ข้อบังคับที่ตั้งไว้ในฐานข้อมูล (ไม่ใช่แค่ฝั่งหน้าจอ):
  - type ต้องเป็น RECEIVE / ISSUE / TRANSFER / ADJUST / SALE เท่านั้น
  - pay_method ต้องเป็น CASH / TRANSFER / CARD
  - จำนวนที่จัดวางในช่องเก็บ (qty) ต้องไม่ติดลบ
  - จำนวนในรายการขายต้องมากกว่า 0
  - รหัสช่องเก็บห้ามซ้ำภายในคลังเดียวกัน
  - สินค้าหนึ่งรายการอยู่ในช่องเก็บเดียวกันได้แถวเดียว (unique)
  - รายการ TRANSFER ต้องมี wh_to และ wh_to <> wh_id  (กันโอนเข้าคลังตัวเอง)
  - ลบสินค้า -> รายการเคลื่อนไหวที่อ้างถึงถูกลบตาม (on delete cascade)
  - ลบคลังที่ยังมีรายการอ้างอยู่ไม่ได้ (on delete restrict)

การเข้าถึงตารางต้องผ่าน 2 ด่าน (สำคัญ — เคยพลาดตรงนี้)
  ด่าน 1  GRANT ระดับตาราง ให้ role authenticated
          ไม่ผ่าน -> HTTP 403 / SQLSTATE 42501 "permission denied for table"
  ด่าน 2  RLS policy
          ไม่ผ่าน -> อ่านได้ผลว่าง หรือเขียนไม่ได้ ("new row violates ...")

RLS: เปิดทั้ง 7 ตาราง อนุญาตเฉพาะ role = authenticated
     anon key เพียงอย่างเดียวอ่าน/เขียนไม่ได้ ต้อง login ก่อนเสมอ

หมายเหตุชื่อคอลัมน์: ใช้ min_qty และ user_name แทน min / user
เพราะ user เป็นคำสงวนของ SQL — การแปลงชื่อทำที่ lib/api.js

# หน้าจอผังที่เก็บสินค้า (Locations)

แนวคิด: แต่ละคลังมี "ช่องเก็บ" หลายช่อง วางเป็นผังด้วยโซน (แถว) และลำดับ (คอลัมน์)
        เช่น A-01 A-02 A-03 A-04 / B-01 ... / C-01 ...
        ข้อมูลตั้งต้นสร้างให้ 3 โซน × 4 ช่อง = 12 ช่องต่อคลัง (รวม 120 ช่อง)

การใช้งาน:
  - เลือกคลัง แล้วจะเห็นผังเป็นตาราง แต่ละช่องบอกรหัส จำนวนที่เก็บ และแถบระดับความเต็ม
  - สีจุดมุมขวาบนบอกประเภทช่อง: ชั้นวาง / พื้นวางกอง / ห้องเย็น / วัตถุอันตราย
  - คลิกช่อง -> เปิดแผงจัดการ เลือกสินค้าและจำนวน แล้วกด "วางลงช่องนี้"
  - มีตารางแจ้ง "สินค้าที่ยังไม่ได้ระบุตำแหน่งครบ" เทียบยอดคงเหลือกับยอดที่จัดวางแล้ว
  - พิมพ์ผังออกเป็นเอกสารได้

ข้อจำกัดที่ตั้งใจ: การจัดวางเป็น "แผนผังการเก็บ" ไม่ใช่ตัวตัดสินยอดคงเหลือ
ยอดคงเหลือยังคำนวณจาก txns ที่เดียวเสมอ ระบบจะกันไม่ให้วางเกินยอดคงเหลือจริง
และกันไม่ให้เกินความจุของช่อง แต่ถ้ามีการรับ/เบิกภายหลัง ผังจะไม่ขยับตามเอง
ต้องมาปรับเอง (ตารางเตือนด้านล่างจะบอกว่ารายการไหนยังไม่ครบ)


# หน้าจอขายสินค้า POS

เพิ่มสินค้าลงบิลได้ 3 ทาง:
  1. ยิงบาร์โค๊ด  — ช่องรับสแกนโฟกัสอัตโนมัติ เครื่องสแกนทำงานเหมือนแป้นพิมพ์
                    ยิงแล้วกด Enter ระบบเพิ่มสินค้าให้ทันที
  2. คีย์เอง      — พิมพ์บาร์โค๊ดหรือรหัสสินค้า (P001) ในช่องเดียวกันแล้วกด Enter
  3. กดเลือก      — คลิกการ์ดสินค้าที่แสดงรูปภาพ ราคา และยอดคงเหลือ

ฟีเจอร์อื่น:
  - เพิ่มรูปสินค้าได้จากหน้า POS เลย (ปุ่ม "เพิ่มรูป" บนการ์ดที่ยังไม่มีรูป)
  - แก้จำนวนในบิลได้ ส่วนลด VAT 7% คำนวณอัตโนมัติ
  - ปุ่มลัดรับเงิน +100 +500 +1000 และ "พอดี" คำนวณเงินทอนให้
  - กดชำระเงินแล้วพิมพ์ใบเสร็จรับเงินทันที และพิมพ์ซ้ำได้จากรายงาน "บิลขาย / ใบเสร็จ"

การตัดสต็อก: บันทึกบิลแล้วระบบสร้างรายการชนิด SALE ตัดสต็อกทันที
             ยอดคงเหลือจึงมาจาก txns ที่เดียวเหมือนเดิม ไม่มีการนับสองที่
             ระบบตรวจสต็อกทั้งตอนเพิ่มลงบิลและตอนกดชำระเงิน ขายเกินสต็อกไม่ได้

ใบเสร็จ: จัดหน้ากว้าง 78 มม. ใช้ได้ทั้งเครื่องพิมพ์ใบเสร็จความร้อนและกระดาษ A4


# วิธีทำงานของข้อมูล

โหลด : เข้าระบบสำเร็จ -> InventoryProvider ดึง products/warehouses/txns ทั้งหมด
       มาเก็บในหน่วยความจำครั้งเดียว (แบ่งหน้าครั้งละ 1000 แถว)
       ทุกหน้าจอจึงเร็วเพราะคำนวณจากหน่วยความจำ ไม่ยิง query ซ้ำ

เขียน : เขียนขึ้น Supabase ก่อนเสมอ ถ้าสำเร็จจึงอัปเดตหน่วยความจำ
       ถ้าเขียนพลาด สถานะบนหน้าจอจะไม่เปลี่ยน และขึ้นข้อความแจ้งเตือน
       (ไม่ใช้ optimistic update เพื่อกันหน้าจอกับฐานข้อมูลไม่ตรงกัน)

เลขที่เอกสาร : คำนวณจากเลขสูงสุดที่มีอยู่จริงใน txns ไม่ใช้ตัวนับแยก
              เพราะฐานข้อมูลใช้ร่วมกันหลายเครื่อง ตัวนับฝั่ง client จะไม่ตรงกัน

# ผลการทดสอบ (2026-08-28)

ก. ตรวจโครงสร้างโค้ด 36 ไฟล์ — ผ่านทั้งหมด
   - import ทุกเส้นทางมีไฟล์จริง และชื่อ named import มี export จริง

   ผังที่เก็บสินค้า        สร้างช่องครบ 120 ช่อง, รหัสช่องไม่ซ้ำในคลัง,

# ข้อจำกัดที่ควรทราบ
- เลขที่เอกสารของ รับ/เบิก/โอน/ปรับปรุง คำนวณฝั่ง client
  ถ้าผู้ใช้ 2 คนกดบันทึกพร้อมกันในเดือนเดียวกัน อาจได้เลขซ้ำได้
  (ตาราง txns ไม่ได้บังคับ unique บน doc_no)
  ถ้าต้องการกันจริงจัง ให้ย้ายไปออกเลขด้วย Postgres sequence ฝั่งเซิร์ฟเวอร์
  * ยกเว้นบิลขาย (sales) ที่มี unique index บน doc_no แล้ว ถ้าซ้ำจะถูกปฏิเสธ

- การจัดวางสินค้าในผังคลังเป็น "แผนผังการเก็บ" ไม่ใช่ตัวตัดสินยอดคงเหลือ
  ถ้ามีรับ/เบิกภายหลัง ผังจะไม่ขยับตามเอง ต้องมาปรับเอง
  (ตารางเตือนในหน้าจอจะบอกว่ารายการไหนยังระบุตำแหน่งไม่ครบ)
- ข้อมูลถูกโหลดมาทั้งหมดตอนเข้าระบบ เหมาะกับข้อมูลระดับหลักหมื่นแถว
  ถ้าโตกว่านั้นควรเปลี่ยนไปโหลดเฉพาะช่วงที่ดูอยู่
- รูปสินค้าเก็บเป็น data URL ในคอลัมน์ text ถ้ามีรูปเยอะควรย้ายไปใช้ Supabase Storage
- ผู้ใช้ที่ล็อกอินแล้วทุกคนมีสิทธิ์เท่ากันทั้งหมด (อ่าน/เขียน/ลบได้ทุกอย่าง)
  ยังไม่มีระบบแบ่งบทบาท เช่น ผู้ดูแล / เจ้าหน้าที่คลัง / ผู้อ่านอย่างเดียว
- แผนที่ต้องเชื่อมต่ออินเทอร์เน็ต (Google Maps Embed)
- ระบบต้องออนไลน์ตลอด ใช้งาน offline ไม่ได้แล้ว (ต่างจากรุ่น localStorage เดิม)
- ยังไม่มีการยกเลิก/คืนสินค้าจากบิลขาย ถ้าขายผิดต้องใช้หน้าจอปรับปรุงสินค้าแก้ยอดเอง
- ตรวจ SQL ได้แค่เชิงข้อความ ไม่มี PostgreSQL ในเครื่องสำหรับรันจริง
  บั๊กเชิงไวยากรณ์จึงหลุดไปได้ (เคยเกิดจริงกับ %L/%I) ตอนนี้มีเทสต์ดักบางส่วนแล้ว

        หรือใช้ปุ่ม "ข้อมูล" > "ตรวจสอบระบบตอนนี้" ในแอป ซึ่งตรวจให้ทีละรายการ

อาการ: ERROR 42601 syntax error at or near "'ชื่อ policy'"
สาเหตุ: ใน DO block ใช้ format('drop policy ... %L ...') กับชื่อ policy
        %L สร้าง string literal (') แต่ชื่อ policy เป็น identifier ต้องใช้ %I (")
        และเพราะ SQL Editor รันทั้งไฟล์เป็น transaction เดียว ทุกอย่างจึง rollback
        ตารางไม่ถูกสร้างเลย ทำให้ตามมาด้วย PGRST205 ตอนเปิดแอป
วิธีแก้: แก้แล้วใน schema.sql (ใช้ %I ทั้งชื่อ policy และชื่อตาราง)
        มีเทสต์ดักไว้แล้วไม่ให้พลาดซ้ำ

อาการ: PGRST205 "Could not find the table 'public.xxx' in the schema cache"
สาเหตุ: 1) ยังไม่ได้รัน schema.sql เวอร์ชันที่มีตารางนั้น หรือ
        2) รันแล้วแต่ PostgREST ยังไม่รีเฟรช schema cache
วิธีแก้: รัน supabase/schema.sql ทั้งไฟล์ (ท้ายไฟล์มี notify pgrst, 'reload schema' แล้ว)
        ถ้ายังไม่หาย ให้รันคำสั่งนี้เดี่ยว ๆ แล้วรอ 5 วินาที:
            notify pgrst, 'reload schema';
หมายเหตุ: ตั้งแต่ 2026-08-28 ระบบไม่พังทั้งแอปแล้ว ถ้าตารางของฟีเจอร์ใหม่หายไป
        จะปิดเฉพาะหน้าจอนั้นและขึ้นวิธีแก้ให้ ส่วนอื่นใช้งานต่อได้

อาการ: "Email not confirmed"
วิธีแก้: Authentication > Users > แก้ผู้ใช้นั้น แล้วยืนยันอีเมล
        หรือสร้างใหม่โดยติ๊ก Auto Confirm User
